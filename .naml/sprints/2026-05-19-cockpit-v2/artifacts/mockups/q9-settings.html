Question 09 / Settings

How is the Settings page organized?

Settings has to carry: project config (gates, base branch, slug), lane count, account / CLAUDE_CONFIG_DIR, sync cadence, label vocabulary, ADR folder — plus the Health page (trend graphs and long-horizon analytics). Trade-off: tabbed nav, long scroll, or first-run wizard.
← all ← Q8b
RECOMMENDATION
Option A — left-nav tabbed page with Health as a top section. Six sections: Project · Lanes · Gates · Account · Sync · Health · Advanced. Health gets the most generous canvas because it's where trend graphs from Q7b live. The tabbed structure lets the daily settings (gates, lane count) stay terse while Health is allowed to sprawl. No wizard — first-run uses the existing /setup-naml skill in the terminal, not a UI flow.

Six tabs cover the whole config surface without crowding any of them. Project / Lanes / Gates / Account / Sync stay terse (forms). Health gets the most generous canvas (trend graphs from Q7b). Advanced hides feature flags, compaction triggers, debug toggles. Settings stays a calm, low-frequency view — you visit it to change something, not to monitor.

WINS
  • Scales as features grow (add tabs)
  • Health is loud without crowding daily settings
  • One-click jump to any section
  • Multi-project surface (top of nav: "Add project…")
COSTS
  • Two-click depth to anything (settings tab → section tab)
  • Search would need to span tabs (defer)

Single scrollable page with a sticky anchor rail at the top. Everything visible by scrolling; cmd-F finds any setting. Simple to extend (just append a section).

WINS
  • Browser cmd-F just works
  • One scroll = whole config
  • Easiest to extend
COSTS
  • Health graphs overshadow simple inputs by sheer height
  • Page gets long fast (8+ sections)
  • Mobile-style scrolling — feels less "cockpit"

First-run wizard walks through every setting once. After completion, the same page acts as a normal settings page (tabbed). Useful for onboarding; redundant after that.

WINS
  • Great first experience
  • Hand-holds nontrivial config
  • Verifies each step before next
COSTS
  • Setup already exists as a CLI skill (/setup-naml)
  • Wizard duplicates that skill
  • Most users will only ever tweak one setting at a time

Side decisions on A:
  • Health as a top-level route or inside Settings? Inside Settings is cleaner (header stays Dashboard/Sprint/Settings as Q1 decided). But Health is half-analytics, not just config — would you rather promote it to a 4th header tab?
  • Multi-project — left nav has "+ Add project…" at the bottom that runs /setup-naml. Project switcher stays in the header (Q2 decision). Confirm that's the model.
  • Save behaviour — autosave on field blur, or explicit "Save" button per section? My pick: autosave with a discrete "Saved 2s ago" badge — fewer modal moments.
  • Advanced tab contents — feature flags, JSONL compaction trigger, "reset aggregates" button, "wipe sprint history", expose config.toml raw editor. Anything you want bumped up out of Advanced into a primary tab?
