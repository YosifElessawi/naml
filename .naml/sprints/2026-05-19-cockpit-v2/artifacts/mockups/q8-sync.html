Question 08 / Sync & smoothness

How does the cockpit stay synced with the run?

Naml already writes state to JSON files (state/slice-N.status.json, state/sprint.status.json) atomically. The UI question is: how do we get those changes to the browser fast, with no flicker, and recover gracefully when sync drops?
← all ← Q7b
RECOMMENDATION
Option A — SSE push driven by a file watcher on .naml/sprints/*/state/. The Python server uses watchdog (FSEvents on macOS) to watch the state directory. When naml atomically rewrites a status.json, the server emits a Server-Sent Events message with the delta. The browser EventSource applies the patch and animates the affected card. No polling, no held connections beyond one SSE stream, latency < 100ms from state file rewrite to pixel flip.

WINS
  • < 100ms latency from disk → DOM
  • No polling overhead — one open stream per tab
  • File watcher = natural fit for naml's atomic JSON writes
  • EventSource is browser-native, no JS dep
  • Reconnect logic is trivial (EventSource handles it)
  • SSE works over HTTP/1.1 + reverse proxies
COSTS
  • Needs watchdog Python dep (small)
  • FSEvents on macOS is reliable; on Linux/inotify there's a per-process watch limit
  • Multi-tab = multiple SSE streams (one per browser tab)
  • SSE is one-way; user actions still go through normal POST

Unifies both directions on one socket. Real win is for client-initiated actions (Run/Merge buttons would go over WS instead of POST). But naml has only ~5 user-driven actions in the whole flow — overkill to use a duplex channel for that. Adds reconnect/backoff complexity that EventSource solves for free.

WINS
  • One channel, both directions
  • Latency very low
  • Future-proof for richer interactivity
COSTS
  • Manual reconnect/backoff/heartbeat
  • Reverse-proxy quirks more common
  • Library dependency on server side
  • Overkill for naml's action surface
Pick a sync mechanism. Reply A, B, or C.
Side decisions on A:
  • Heartbeat cadence — server emits a ping SSE event every 2s even when nothing's changing. Drives the "Synced Ns ago" badge cheaply. Comfortable, or pull to 1s (snappier but more chatter)?
  • Sync-lost threshold — go SLOW after 5s without ping, LOST after 15s without ping. OK, or tighter (3s / 10s)?
  • Initial state on connect — server's first SSE event is a full snapshot (every sprint + slice). Subsequent events are deltas. So you can refresh the page mid-run and pick up exactly where you left off. Confirm that strategy.
  • Catch-up on reconnect — when SSE reconnects, send a "since=<last-event-id>" so the server can stream missed events. Native to EventSource via Last-Event-ID header. Worth implementing right away, or skip until we hit a real reconnect race?
  • Per-tab vs shared — one SSE stream per tab is the default. Open 4 tabs = 4 streams. Probably fine, but worth knowing.
