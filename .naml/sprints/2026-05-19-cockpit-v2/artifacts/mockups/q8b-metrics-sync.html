Question 08b / Metrics sync — architecture

Where do metrics live, who aggregates them, and is it fast?

State lives in state/*.json files. But metrics — token counts, costs, context window, today/week/lifetime rollups — come from Claude's streaming output, not from disk state. So the question splits in three: where do raw events come from, who aggregates them, and do we need a DB?
← all ← Q8
Short answer: no DB. Append-only JSONL on disk + in-memory aggregator in the server process. Naml is a single-user local tool. Adding SQLite or Postgres is centralization theater for a problem that's already solved by the filesystem. The JSONL files are the database — they're append-only, replayable, debuggable, and small. Aggregations live in RAM and are rebuilt from disk on cold start in < 2 seconds for a 6-month-old project. Latency disk→DOM stays under ~120ms.

WHO HOLDS WHAT · the four tiers, no DB
TierWhereWhat it holds · how it's used
Source of truth disk JSONL Append-only token events per slice. Replayable. Survives restart. Compactable into a daily rollup if files ever get huge (years out).
Server hot cache Python dict in RAM All aggregates: per-slice, per-sprint, per-day, per-week, per-30d, lifetime. ~3MB for a 6-month-old project. Rebuilt on cold start from JSONL.
Wire SSE event Two event types: state-update (slice transitions) and metric-tick (token deltas + fresh rollups). Browser is "dumb client".
Browser store plain JS object Mirror of relevant slice / sprint / project rollups. Patched by SSE events. Single-source: never queries server, only receives.
WHY NO DB · the question you asked
ConcernWithout DBWith SQLite
Cold-start latency ~1–2s scan of JSONL (6-mo project, ~50MB total) ~50ms · one query
Per-event latency ~50ms total (write + parse + agg + emit) ~50ms · same path + extra row insert
Disk footprint JSONL is the file · readable in any editor +1 binary SQLite file · same data, opaque
Debugging tail -f *.tokens.jsonl · trivial Need sqlite3 CLI or DB tool
Time-window queries In-memory rollups are O(1) reads · pre-aggregated Indexed SQL · also O(1) for hot keys
Reset / wipe a project rm -rf .naml/sprints/<id> DELETE FROM rows + rm files (two steps to keep in sync)
Backup Already part of git if tracked, or trivial tar Need SQLite-aware backup (BEGIN IMMEDIATE)
Concurrent writers Each lane appends to its own JSONL · zero contention SQLite WAL handles it, but it's contention you didn't have
Multi-tab / multi-server Server is the only reader · no problem Same
Future: cross-project rollups Scan all .naml/ dirs on cold start · still < 5s Single SQL query — slightly faster
The one case where SQLite would earn its keep: if you ever want cross-project historical analytics in the UI ("show me my last 6 months across all projects, ranked by cost-per-merged-PR"). Today: cockpit is per-project, so no. If you add an "All Projects" view later, revisit then. Easy to bolt SQLite on as a materialized view over the JSONL when needed — JSONL stays source of truth.
EDGE CASES THIS COVERS
CaseBehaviour
Server crashes mid-sprint JSONL on disk is intact. Restart → cold replay → exactly where we left off.
Browser refreshes mid-sprint EventSource reconnects. Server's first event is a full snapshot of current state + rollups. Then deltas.
Lane crashes (Claude session dies) JSONL has events up to the crash. Slice marked failed. Aggregates still correct because no event is double-counted.
Manual JSONL edit (you fix a bad row) fsevents fires → server detects file rewrite → replay from scratch for that file → re-emit corrected rollups.
Disk fills up JSONL write fails → lane logs error, retries → if persistent, sprint pauses with diagnostic. Aggregates frozen at last successful write.
Years go by, JSONL files get big Periodic compaction job: any sprint > 90 days old gets its JSONL replaced with a single summary.jsonl line. Aggregates unchanged. (Not needed for v1.)

Two concrete decisions to make:
  • Claude output mode — confirm: lanes spawn claude -p --output-format stream-json so we get per-turn usage blocks. Roadmap Phase A already calls for this. Without it, we get cost only at session end, which kills live cost telemetry.
  • Context-window % — derive from tokens_in + cache_read running total ÷ model max (e.g. 200k for Sonnet 4.6). Confirm we use the model's context window from config.toml, not a hardcoded constant.
  • "Lifetime" origin — first JSONL event we ever see for this project. So lifetime starts the moment the first slice runs. OK?
  • Cross-project aggregates (account-level "today $") — server scans all ~/Desktop/Naml/projects JSONL files OR we have a single global ~/.naml/usage.jsonl that every lane also appends to. My pick: scan all per-project JSONLs on cold start (no double-write); cache the cross-project aggregate in RAM.
  • Compaction — defer to v2. JSONL files stay raw until they become a problem (won't for years on a personal tool).
