Question 05 / Slice cards

What goes on a slice card?

Slice cards are the densest information surface in the cockpit. They have to carry: state, duration in state, context-window %, token cost, retry attempts, session ID, branch + PR, review verdict, last gate. Trade-off: how much telemetry per card vs. how many cards fit on screen.
← all ← Q4
RECOMMENDATION
Option A — dense telemetry cards (~110px). Title + state pill on row 1, dual progress bars on row 2 (duration vs. budget + context window %), stats strip on row 3 (cost, retries, branch, session-id with copy/terminal buttons). Mini traversal pill chain underneath shows the path through states. The context-window meter is the highest-value signal — it turns amber at 70%, red at 85% — that's your "smoke" alarm before a slice burns out.

Each card answers four questions instantly: where is it in the state machine, is it taking too long, is it about to run out of context, how much has it cost so far. Context-window meter turns amber at 70%, red at 85% — that's the most actionable signal in the entire cockpit. Session-ID + buttons (copy / open-terminal / view-branch) let you intervene in one click.

WINS
  • Context window % = "smoke alarm"
  • Duration vs. budget = pacing
  • Session controls inline
  • State traversal shows retry history
COSTS
  • ~110px per card — ~5 cards/screen
  • Many fonts/colors per card
  • Could overwhelm at 8+ slices

Single-line card. State icon + title + slice-progress bar + cost + time. Everything else (context window, retries, gate, session) lives in a click-through drawer. Calm, simple — but you lose at-a-glance "is this slice about to die" awareness.

WINS
  • ~40px per card — 12 fit on screen
  • Visually calm during long runs
  • Easy for non-technical users
COSTS
  • Context-window smoke alarm hidden
  • Retries hidden
  • Need a click to act
  • Doesn't feel like a "cockpit"

Slim table. Every metric in a column. Maximum scannable density — 12–15 slices fit without scroll. Best for sprints with many slices. Less character; reads like a CI dashboard.

WINS
  • Densest possible — all info, all rows
  • Sortable / filterable

COSTS

  • Stats less prominent (tiny numbers)
  • Less "alive" — no animation per slice

A few micro-decisions inside A:
  • Duration budget — I show a ~9m budget tick mark. Sourced from? (a) hardcoded default per state, (b) learned from past slices in this project, (c) drop the budget mark entirely. I'd default to (a) until enough history, then auto-learn.
  • Context-window thresholds — amber at 70%, red at 85%. Comfortable, or pull them tighter (60/80)?
  • Stats strip overflow — if cost + tokens + retry + gate + session don't fit, what gets dropped first? My pick: tokens detail (collapse to just $cost; expand on hover).
