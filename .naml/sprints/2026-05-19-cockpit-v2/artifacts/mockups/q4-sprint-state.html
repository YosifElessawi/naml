Question 04 / Sprint state machine

How do we show the sprint's state in motion?

Sprint flows through planning → publishing_issues → executing → awaiting_signoff → merging → complete, with branches to failed, partial_failure, merge_blocked. The viz has to read at a glance, surface duration in each state, and animate transitions live.
← all ← Q3
RECOMMENDATION
Option A — horizontal pill stepper with sub-rail. Six pills on a rail (one per main state). Current pill pulses, completed ones are solid. Tiny duration under each pill shows time spent. Inside the executing pill, a 1px-tall sub-rail of slice-state cells gives you the live slice shape without leaving the sprint state view. Failure branches collapse into a muted "alternate exits" strip below, only highlighted if the sprint actually hits one.

The stepper reads in < 1 second. The sub-rail inside executing shows the active slice shape so you don't have to scroll to slice cards to know the overall pulse. Failure branches stay visible but de-emphasized — they exist for awareness, light up only if hit. ETA derives from mean per-slice duration so far × remaining slice count.

WINS
  • State + duration + ETA in one rail
  • Slice shape visible inside the state pill
  • Animated pulse = "still alive" signal
  • Failures don't dominate when they're not happening
COSTS
  • Doesn't show the graph structure (loops, retries)
  • Past-state durations are tiny — easy to miss
  • Retries inside a state aren't visible

Each transition is logged with exact timestamp, duration in state, and a one-line detail. Reads like a CI build log. Best for post-mortems and audit; less ideal as the always-on live status.

WINS
  • Full traversal history captured
  • Exact timestamps for every transition
  • Detail per state worth keeping
  • Great for replay / debug
COSTS
  • Vertical = tall — eats real estate
  • Slow to read "where am I" — eye has to scan
  • Future states feel hypothetical
OPTION C

Schematic graph · nodes & edges (mirrors design-doc diagram)

traversed current possible terminal

A real graph: nodes for every state, edges for every transition, including the failure terminals from the design-doc state diagram. The traversed path is solid green; the current state is the lit cyan node; everything else is dim. Closest to how engineers think about state machines.

WINS
  • Full state-machine fidelity
  • Failure exits are visible
  • Engineer-flavored — feels honest
  • Doubles as documentation
COSTS
  • Takes more vertical space
  • Heavier to render & animate
  • Reads slower than a stepper
  • Possibly intimidating to non-engineers
